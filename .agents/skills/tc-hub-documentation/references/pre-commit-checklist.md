# Pre-Commit Checklist

> **Last updated:** 2026-11-03
> **Docs generated by:** Cline agent (model not recorded)

Run through every item before committing any documentation change:

- [ ] Language: 100% English (prose, comments, tags).
- [ ] Markdown: `> **Last updated:**` date = today, `> **Docs generated by:**` = the model that made the change (both refreshed on every edit).
- [ ] Markdown: exactly one H1; correct title form (`NN — Topic`, `@Name Annotation`, `<Topic> Documentation — Index`); no skipped heading levels.
- [ ] Markdown: every code identifier in backticks; tables use `| --- |` separators; `---` rules only in reference/annotation docs; no images.
- [ ] Markdown: all links relative and resolvable (files exist, anchors match headings, `§N.M` references still valid); new folders registered in `documentation/00-Overview.md` and `14-Related-Documentation.md`.
- [ ] Markdown: annotation docs follow the `1. The Annotation → 2. How It Works → 3. Examples → 4. Where It's Implemented → 5. Comparison` skeleton; attribute tables complete.
- [ ] ADRs: built from [adr-template.md](../adr-template.md); named `ADR-NNN-kebab-case-title.md` with the next free number; H1 form `# NNN — <Title>`; new ADRs registered in `ADRs/00-Overview.md`, and the overview row synced in the same commit whenever an existing ADR changes.
- [ ] JavaDoc: every new/changed type and non-trivial method has Javadoc; stale Javadoc removed; legacy `@author/@date/@history` not introduced.
- [ ] JavaDoc: `@since` + `@docs generated by` are the last two tags and refreshed on every change; `{@code documentation/...}` pointers resolve to docs that actually cover the type.
- [ ] Code samples in docs are real project code (or clearly minimal variants) and still compile against the current API.
- [ ] No changes under `target/generated-sources/**`; OpenAPI descriptions changed in `src/main/resources/oas/*.yaml` only.
- [ ] Code change and its doc update are committed together.

## Instructions for AI Assistants

This skill is binding when new documentation is created or existing documentation is revised. Follow these imperative rules in order:

1. **Language.** Write all documentation (Markdown, Javadoc, comments, OAS descriptions) in English only.
2. **Metadata first.** Before writing any content, decide the `Last updated` date (today) and the model name for the attribution line; place the metadata header (Markdown) or `@since`/`@docs generated by` tags (Javadoc) in the document.
3. **Find the template.** Identify the document kind (chapter, annotation doc, topic index, topic file, README, ADR) and replicate its established structure exactly; for ADRs, start from [adr-template.md](../adr-template.md); do not invent new section orders.
4. **Verify before linking.** Resolve every link, anchor, and `{@code documentation/...}` pointer against the file system before committing; fix or remove broken references in the same commit.
5. **Match the code, not the other way round.** Read the implementation before documenting it; if code and documentation disagree, treat the code as truth and update the documentation (flag the discrepancy to the user).
6. **Update in place.** Modify the existing document that covers the changed topic; create a new document only for genuinely new topics, and then register it in `documentation/00-Overview.md` and `14-Related-Documentation.md` (ADRs: in `documentation/ADRs/00-Overview.md`, also whenever an existing ADR changes).
7. **Do not invent rules or content.** If a convention is not covered by this skill or by the existing documentation, follow the majority pattern of the nearest sibling document and note the assumption.
8. **Minimal diffs.** When updating an existing document, change only what is outdated; do not reformat or reword unchanged sections (except refreshing the mandatory metadata header).
