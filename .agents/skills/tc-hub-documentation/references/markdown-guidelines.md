# Markdown Guidelines

> **Last updated:** 2026-11-03
> **Docs generated by:** Cline agent (model not recorded)

Detailed rules for creating and revising Markdown documents in tc-hub. Applies to every Markdown kind: root `README.md`, numbered chapters `documentation/NN-*.md`, per-annotation docs `documentation/annotations/*.md`, ADRs (see [adr-guidelines.md](adr-guidelines.md)), topic deep-dive folders `documentation/<topic>/NN-*.md`, and the `00-Overview.md` index files.

## Document landscape

| Location                         | Kind                                                                             | Naming                                       |
| -------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------- |
| `README.md` (repository root)    | Project overview (stack, structure, build, testing)                              | fixed name                                   |
| `documentation/NN-*.md`          | Numbered chapters 00–14: short summaries + chapter index                         | `NN-Topic-Name.md`                           |
| `documentation/annotations/*.md` | Exhaustive per-annotation reference docs                                         | `<AnnotationName>.md` (exact Java type name) |
| `documentation/<topic>/NN-*.md`  | Topic deep dives (`aop`, `build`, `conversions_and_mappings`, `spel`, `testing`) | `00-Overview.md` index + `NN-Topic.md`       |
| `documentation/ADRs/*.md`        | Architecture Decision Records (one ADR per decision)                             | `ADR-NNN-kebab-case-title.md`                |

### Derived style facts

- **Language & tone:** English, factual, concise, technical; no second person; no marketing language; backticks on every code identifier; em dash `—` as prose separator; **bold** for key terms on first mention.
- **Detail level:** chapters stay short (nested bullet lists, at most small tables); deep content lives in topic folders; annotation docs are exhaustive (behavior, real-code examples, implementation locations, sibling comparisons).
- **Attribution:** docs either record an explicit model name (majority, e.g. `hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL`) or `Cline agent (model not recorded)` (older docs). Record the explicit model name whenever it is known; use `Cline agent (model not recorded)` only when it truly is not.

## Purpose and audience

1. Document the tc-hub architecture, mapping/conversion frameworks, annotations, and workflows for developers and AI assistants who implement or maintain the code.
2. State the document's purpose within the first one or two sentences after the metadata header.

## File structure and naming

1. Keep the existing layout: root `README.md`; numbered chapters in `documentation/`; per-annotation docs in `documentation/annotations/`; ADRs in `documentation/ADRs/`; deep dives in a dedicated `documentation/<topic>/` folder.
2. Name chapter and topic files `NN-Topic-Name.md`: two-digit zero-padded prefix, ASCII, no spaces, hyphens between words, PascalCase words (e.g. `12-Steps-For-Implementing-New-Functionality.md`).
3. Name annotation docs exactly after the Java type, without `@` (e.g. `@TcNestedObject` → `TcNestedObject.md`).
4. Every topic folder must contain `00-Overview.md` as its index.
5. Do not add `README.md` files inside `documentation/` — use `00-Overview.md`.

## Document header (mandatory)

Every Markdown document starts with exactly:

1. one `# ` (H1) title,
2. a blank line,
3. the two-line metadata blockquote:

```markdown
> **Last updated:** YYYY-MM-DD
> **Docs generated by:** <LLM model name, or "Cline agent (model not recorded)">
```

4. On every change, update **both** lines (date = change date, model = the model that made the change).

H1 title forms:

- Chapters: `# NN — Topic Name` (em dash, e.g. `# 05 — Conversions / Mappings`).
- Annotation docs: `# @<Name> Annotation` (e.g. `# @TcCompoundProperty Annotation`).
- Topic indexes: `# <Topic> Documentation — Index` or `# <Topic> in tc-hub` (e.g. `# AOP Documentation — Index`, `# SpEL Expressions in tc-hub`).

## Structure of new documents

1. **Annotation doc** (`documentation/annotations/<Name>.md`) — follow this exact skeleton (the majority pattern in `TcCompoundProperty.md`, `TcNestedObject.md`, `TcTest.md`, `ContextError.md`):
   - H1 + metadata header.
   - Intro paragraph: what the annotation does and when it is used; key terms **bold**; backticks on identifiers.
   - Metadata bullet list: `- **Annotation:** <FQCN>`, `- **Module:** <maven-module>`, plus the applicable extra entries (e.g. `- **Repeatable container:**`, `- **Supported mappers:**`, `- **Aspect:**`, `- **Handler:**`, `- **Configuration container:**`).
   - A `---` horizontal rule before every top-level `##` section.
   - `## 1. The Annotation` — the complete annotation source in a ```java fence, then an attribute table `| Attribute | Type | Default | Description |`, then bullets for **Target** / **Retention** / meta-annotation facts.
   - `## 2. How It Works` — mechanism walkthrough with numbered subsections `### 2.1 …`; include short ```java snippets of the relevant framework code.
   - `## 3. Examples` — `### Example 1 — <scenario>` blocks with ```java code based on real domain code where possible.
   - `## 4. Where It's Implemented` — table `| Concern | Location |` with repository-relative paths (prefix `src/java/…`); abbreviate long repeated path prefixes as `.../`.
   - `## 5. Comparison with Sibling Annotations` (only when siblings exist) — comparison table with the subject's row **bold**.
   - Final cross-reference section: prose links to the framework doc(s) and related chapter(s), with section anchors.
2. **Topic index** (`documentation/<topic>/00-Overview.md`) — follow `aop/00-Overview.md`, `build/00-Overview.md`, `testing/00-Overview.md`:
   - H1 + metadata header.
   - One sentence: "This directory contains the detailed <topic> documentation for tc-hub, as a companion to [NN-Chapter.md](../NN-Chapter.md)."
   - `| File | Content |` table listing every file of the folder with relative links.
   - An "at a glance" overview: summary table and/or ASCII diagram in a plain code fence.
   - `## Related documentation` — bullets linking chapters and annotation docs outside the folder.
3. **Chapter** (`documentation/NN-Topic.md`) — keep it short: H1 + metadata header, then `##` sections of nested bullet lists (dash-separated descriptors); offload deep content to a topic folder via a `> **Deep dive:** [folder/](folder/00-Overview.md)` blockquote (see `05-Conversions-Mappings.md`).
4. **Chapter index** (`documentation/00-Overview.md`) — table `| # | Chapter | Summary |` with one linked row per chapter; unnumbered topic folders get `| — |` rows.

## Headings

1. Use exactly one H1 per file (the title). Never skip levels (H2 → H4 is forbidden).
2. Chapters and deep-dive docs: `##` for top-level sections. Number them when the doc is a reference with a fixed section order (`## 1. …`, `## 2. …`, …); leave them unnumbered for narrative chapters (`## Technology Stack`).
3. Subsections: `### 2.1 …` numbering under numbered sections; plain `### Example N — <scenario>` for examples.
4. Cross-referencing sections by number is allowed and used (`see §2.5`, `[03-Aspects.md §3.1](03-Aspects.md)`); keep the referenced heading text stable when it is referenced this way.

## Formatting

1. Inline code: wrap every class, method, annotation, field, property, config key, file name, and command in backticks (`` `ModelObject` ``, `` `@TcInfo` ``, `` `bsh.error.context` ``, `` `src/java/pom.xml` ``).
2. Bold: key terms, annotations, and the subject of a comparison row (`**bold**`); never bold whole sentences.
3. Lists: `-` bullets for facts and nested structure; numbered lists only for ordered steps (e.g. `12-Steps-For-Implementing-New-Functionality.md`).
4. `---` horizontal rules separate top-level numbered sections in annotation/deep-dive docs; do not use them in short chapters.
5. Em dash `—` with surrounding spaces separates clauses; `…` ellipsis for trailing "etc."
6. No trailing whitespace; one blank line around headings, tables, code fences, and blockquotes.

## Code blocks

1. Use fenced blocks with a language tag when the content is code (`java`, `yaml`, `powershell`); use an untagged fence only for ASCII diagrams (flowcharts, advice stacks, module trees — see `ObjectPolicy.md` §2.1, `aop/00-Overview.md` "advice stack").
2. Code must be real, compiling project code (or clearly minimal variants of it); include the `package` line in annotation source listings.
3. In snippets, use `//` comments to explain intent (e.g. `// ✅ goes through proxy → aspect fires`, `// ⚠ SELF-INVOCATION — proxy bypassed!`).
4. Keep snippets focused on the documented behavior; elide unrelated bodies with `...`.

## Links

1. Use relative Markdown links with a readable label: `[TcNestedObject.md](annotations/TcNestedObject.md)`, `[02-Use-Case-Mapping.md](02-Use-Case-Mapping.md)`.
2. Link to a specific section by appending the GitHub-style anchor: `[03-Tc-Mapping-Framework.md, section 4](../conversions_and_mappings/03-Tc-Mapping-Framework.md#4-providers--the-per-direction-callbacks)`; the anchor is generated from the heading (lowercase, spaces → `-`, punctuation dropped).
3. From a topic folder, reference chapters with `../NN-Topic.md`; from a chapter, reference topic files with `topic/NN-File.md`; from annotation docs, reference other annotations in the same folder without a prefix.
4. Register every new chapter/topic folder in `documentation/00-Overview.md` (the `| # | Chapter | Summary |` table) and in `documentation/14-Related-Documentation.md`.
5. Never link absolute paths or `file://` URIs; never invent links to files that do not exist.

## Tables, images, diagrams

1. Tables are the primary reference vehicle: use them for attributes, implementations, file indexes, module trees, comparisons. Use `| --- |` separator rows; keep cells short — long explanations belong in prose before/after the table.
2. Common table shapes: `| Attribute | Type | Default | Description |`, `| Concern | Location |`, `| File | Content |`, `| # | Chapter | Summary |`, `| Module | Role |`.
3. No images exist anywhere in the documentation — do not add images. Use ASCII diagrams in plain code fences for flows and hierarchies.
4. Use `✅` / `⚠` markers sparingly, only to contrast "works" vs. "does not work" examples.

## Change documentation

1. There is no separate changelog file: the "change documentation" is the mandatory metadata header. On every edit, update `**Last updated:**` to the change date and `**Docs generated by:**` to the model that made the change.
2. Keep affected cross-references in sync: if a section moves or is renamed, update every link/anchor/`§N.M` reference to it.
3. When a code change alters documented behavior (annotation attribute, config key, aspect order, command line), update the corresponding doc in the same commit.
4. If a documented fact becomes obsolete, remove or correct it — do not leave stale statements marked "old".

## Do's and Don'ts

- **Do** write in the present tense, third person, without addressing the reader.
- **Do** keep chapters short and push depth into topic folders / annotation docs.
- **Do** reuse the exact section names of the established templates (`The Annotation`, `How It Works`, `Examples`, `Where It's Implemented`).
- **Do** verify that every `{@code documentation/...}` pointer and every Markdown link resolves to an existing file before committing.
- **Don't** use German or any other language than English.
- **Don't** add author names, revision histories, or version numbers to Markdown docs.
- **Don't** duplicate content between a chapter and its topic folder — summarize in the chapter, link the deep dive.
- **Don't** edit generated sources (`target/generated-sources/**`) or describe them as hand-maintained; OpenAPI descriptions live in `src/main/resources/oas/*.yaml`.
- **Don't** create new top-level folders under `documentation/` without adding an entry to `00-Overview.md` and `14-Related-Documentation.md`.
