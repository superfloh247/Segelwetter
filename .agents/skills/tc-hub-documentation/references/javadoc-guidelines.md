# JavaDoc Guidelines

> **Last updated:** 2026-11-03
> **Docs generated by:** Cline agent (model not recorded)

Detailed rules for writing and maintaining JavaDoc in the `src/java` modules of tc-hub.

## When JavaDoc is required

1. Write a class-level Javadoc (type-level `/** ... */` directly above the type declaration) for every **new** class, interface, enum, record, and annotation in `src/java/**`.
2. Write method-level Javadoc when the method's name and signature do not fully convey its behavior: non-obvious semantics, side effects, TC property loading, SpEL usage, special null/empty behavior, or Teamcenter-specific contract (puid vs. buid, policy requirements).
3. Update Javadoc in the same commit whenever a public method or type behavior changes; when a method is removed, remove its Javadoc; never leave stale Javadoc above a method it no longer describes.
4. Every Javadoc comment written by an AI assistant MUST end with the two metadata tags:

```java
 * @since YYYY-MM-DD
 * @docs generated by <LLM model name, or "Cline agent (model not recorded)">
```

## When JavaDoc is not required

1. No Javadoc for trivial getters/setters/constructors, `toString`/`equals`/`hashCode`, Lombok-generated members, or methods that merely delegate with no added contract.
2. No Javadoc on fields except when the field encodes a non-obvious contract (rare; prefer a short `//` comment).
3. Do not add Javadoc to **generated** code: `target/generated-sources/**` (OpenAPI interfaces/models) and Teamcenter strong-type wrappers under `com/teamcenter/**` and the `soa` mirror packages are never hand-edited. Their `@param`/`@return`/`@throws` tags are generator output.
4. Do not backfill Javadoc on legacy files (2018–2020, mechanical-engineering `materiallist` package) when they are touched; only touch a legacy Javadoc if the change requires it.

## Type-level Javadoc (classes, interfaces, enums, records, annotations)

Two hand-written patterns exist (≈495 documented types); use the selection rule:

1. **Pointer pattern** — for framework types whose full reference doc already exists (majority in `common/plm-hub-*` core/tc/rest):

```java
/**
 * Full documentation (behavior, examples, implementation locations):
 * {@code documentation/annotations/TcCompoundProperty.md}
 * {@code documentation/spel/00-Overview.md}
 *
 * @since 2026-09-25
 * @docs generated by hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL
 */
```

- Each `{@code ...}` line MUST point to a doc that actually documents this type (verify before writing; do not copy neighboring files' pointers).
- List multiple docs when the type is covered by several (e.g. a SpEL engine covered by several use-case docs).

2. **Summary pattern** — for types without a dedicated doc, or for annotation types where the Javadoc is the primary short reference:

```java
/**
 * Basic field-level mapping annotation that maps a domain field to a single
 * Teamcenter property (a scalar property such as {@code name} or
 * {@code item_id}). Used in both directions: ...
 * <p>
 * Full documentation (how it works, examples, implementation locations):
 * {@code documentation/annotations/TcProperty.md}
 *
 * @see com.bsh.plm.tc.mapping.annotations.repeatable.TcProperties
 * @since 2026-09-18
 * @docs generated by hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL
 */
```

3. Structure rules for the summary: 1–3 sentences summary first; separate paragraphs with `<p>`; a final paragraph starting with "Full documentation …:" linking the doc(s); wrap literals, property names, and SpEL variables in `{@code ...}`; optional `@see` lines for closely related types (container annotation, validator, factory class).
4. For enum types: describe the meaning of the enum and each constant in one short paragraph (or one line per constant after the summary).
5. `@since` holds the date the Javadoc was introduced/last materially changed (ISO `YYYY-MM-DD`); `@docs generated by …` follows the same attribution rule as Markdown headers.
6. Legacy pattern (pre-2021: `@author`, `@date DD.MM.YYYY`, `@version`, `@history` block) — never use in new or modified code; do not convert legacy files unless explicitly asked.

## Method-level Javadoc

1. First line: short summary in third person present tense, no trailing period on single-line summaries; wrap at the existing ~100-column width.
2. Body (only when needed): one or more short paragraphs separated by `<p>` explaining contract, directionality ("read direction" / "create direction"), or TC semantics.
3. Tags, in this order, only when applicable: `@param` (each parameter), `@return`, `@throws` (each checked exception or non-trivial runtime exception), `@see`.
4. `@param`/`@return`/`@throws` are used in hand-written code only when the information is not self-evident (e.g. `@param uid unique resource identifier (required)`, `@return null when no policy is active`, `@throws ContextErrorException when a Teamcenter error code matches the configuration`); do not write empty `@param name` tags.
5. Do not document implementation details (algorithms, loops) in Javadoc — keep it to the contract.

## Parameter, return, and exception requirements

1. `@param`: name + description. Use the parameter's conceptual name (the TC property name, the SpEL variable), not the Java type.
2. `@return`: state what is returned, including nullability and the mapping direction where relevant.
3. `@throws`: exception type + when it occurs. For Teamcenter errors, reference the context-error mechanism (`ContextErrorException` carrying `ErrorValue` codes) instead of enumerating every code.

## Tag usage rules

1. Standard tags allowed: `@param`, `@return`, `@throws`, `@see`, `@deprecated`.
2. Project-specific tags (always present in AI-assisted Javadoc): `@since YYYY-MM-DD`, `@docs generated by <model>`.
3. Never use `@author` or `@date` in new Javadoc.
4. Order: summary → paragraphs → `@see` → `@since` → `@docs` (last, always the final tag).

## Do's and Don'ts (JavaDoc)

- **Do** keep the two metadata tags on every Javadoc you create or modify, refreshing both on change.
- **Do** point `{@code documentation/...}` references only to docs that document the given type.
- **Do** use `{@code}` for identifiers and literals inside prose.
- **Do** keep Javadoc aligned with the 4-space indentation of the annotated member.
- **Don't** invent behavior that is not in the code; when unsure, read the implementation first.
- **Don't** use HTML beyond `<p>`; no `<h*>`, `<table>`, or `<ul>` in Javadoc (tables live in the Markdown docs).
- **Don't** mix legacy `@author/@history` and new tags in one block.
- **Don't** add Javadoc to generated sources or to `com.teamcenter.**` mirror code.
