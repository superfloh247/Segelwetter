# Project-Specific Documentation Guidelines

> **Last updated:** 2026-11-03
> **Docs generated by:** Cline agent (model not recorded)

## Overview

This skill is the binding rule set for **all** documentation work in tc-hub: creating, updating, and maintaining Markdown documents under `documentation/` (root `README.md`, numbered chapters `documentation/00-Overview.md` … `documentation/14-Related-Documentation.md`, per-annotation docs in `documentation/annotations/`, ADRs in `documentation/ADRs/`, topic deep-dive folders `documentation/{aop,build,conversions_and_mappings,spel,testing}/`) and the JavaDoc in the `src/java` modules. The rules were derived exclusively from the existing tc-hub documentation and the JavaDoc in the `src/java` modules; when two styles coexist in the corpus, the majority pattern wins.

**Use this skill** whenever the task is to write a new document or JavaDoc comment, revise or extend an existing one, create or change an ADR, register a new chapter/topic folder, fix a broken link or stale statement, or review a documentation change before commit.

**Do not use this skill** for documentation-adjacent tasks that do not touch project documentation itself (e.g. plain code comments that are not JavaDoc, OpenAPI YAML editing except for descriptions, or refactoring the `documentation/` tree without changing content — the content rules still apply to whatever is touched).

### Global constraints (always in force)

- **Language:** all documentation (Markdown, Javadoc, comments, OAS descriptions) is written in **English** only — prose, comments, tags.
- **Metadata:** every document carries two metadata facts — the **last update date** and the **generating LLM model**. Markdown: the mandatory two-line header blockquote; JavaDoc: the `@since` + `@docs generated by` tags. Both are refreshed on **every** change (date = change date, model = the model that made the change). Record the explicit model name whenever it is known; use `Cline agent (model not recorded)` only when it truly is not.
- **Tone & style:** factual, concise, technical; present tense, third person; no second person; no marketing language; backticks on every code identifier; em dash `—` as prose separator; **bold** for key terms on first mention.
- **Code is truth:** read the implementation before documenting it; if code and documentation disagree, treat the code as truth and update the documentation (flag the discrepancy to the user). Code samples in docs are real project code (or clearly minimal variants) and still compile against the current API.
- **Update in place:** modify the existing document that covers the changed topic; create a new document only for genuinely new topics, and then register it in `documentation/00-Overview.md` and `14-Related-Documentation.md` (ADRs: in `documentation/ADRs/00-Overview.md`, and sync the overview row whenever an existing ADR changes).
- **Minimal diffs:** when updating an existing document, change only what is outdated; do not reformat or reword unchanged sections (except refreshing the mandatory metadata header).
- **No invented content:** if a convention is not covered by this skill or by the existing documentation, follow the majority pattern of the nearest sibling document and note the assumption.
- **Protected locations:** never edit `target/generated-sources/**` or describe it as hand-maintained; OpenAPI descriptions live in `src/main/resources/oas/*.yaml` only. A code change and its doc update are committed together.
